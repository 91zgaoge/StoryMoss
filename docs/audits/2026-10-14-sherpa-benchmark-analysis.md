# Pocket FM Sherpa × StoryMoss 对标分析

> 日期：2026-10-14
> 缘起：用户提供 Sherpa（Pocket FM 的虚构写作 AI）产品介绍文本，要求「结合本项目实际，深刻分析借鉴，形成分析总结文档」。
> 方法：Sherpa 侧结论**全部取自用户提供的产品介绍原文**——这是一份营销材料。本文只拆解它描述的**产品结构与机制主张**，不采信任何业务数字（原文「55 亿小时的游戏时间」疑为「收听小时数」的翻译误差；$250M→$500M ARR、1200%、55 万创作者等数字均无第三方核验渠道）。StoryMoss 侧由三个并行走查代理逐文件核查当前工作树（v0.65.4），本文引用的每一处结论均带 `file:line`；四条关键论断（检索未接线 / 纲层不重算 / 反馈回路去向 / 卷层空位）由本机 grep 二次复核。
> 核验声明：本文不对 Sherpa 的真实工程能力下判断（我们看不到它的代码）；只回答一个问题——**它宣称的机制里，哪些 StoryMoss 已有、哪些值得引进、哪些是数据护城河层面的不可复制项、哪些在价值观上不该引进**。

## 〇、结论（先读这段）

**一句话**：Sherpa 的「三大技术飞跃」拆开看是两个工程机制加一个数据护城河——状态跟踪/检索、层级规划/局部重规划，StoryMoss 都已具备或已具备一半；而基于留存数据的散文引擎是私域数据资产，结构上不可复制。真正的差距不在三个标题里，而在标题之下的**三条连接组织**：

1. **「状态跟踪与检索」——StoryMoss 把跟踪做到了第一梯队，检索那一半却没接进生成路径**：`QueryPipeline`（token + 语义 + 融合 + 图谱扩展 + 预算控制，四阶段）实现完整但零生产调用方（`memory/query.rs:1` 模块级 `#![allow(dead_code)]`；真正的 RRF 融合在 LanceDB `hybrid_search`，同样未被生成消费）；`WriteTimeBundle` 的参考场景退化为关键词重叠 top 3（`creative_engine/write_time_bundle.rs:213-226`）；LanceDB 混合检索（RRF, `vector/lancedb_store.rs:390-446`）没有一处被续写路径消费。Sherpa 讲的「高速度检索按需呈现精确上下文」，正是这个未接线的模块。
2. **「动态重规划」——StoryMoss 做到了物料层，还没做到纲层**：编辑旧章会触发指纹感知重算（章摘要/段摘要/快照/关系审计，`story_system/recompute.rs`），级联影响报告自动生成（`cascade_rewriter/impact_report.rs`）；但**下游章纲不在失效范围内**——`story_material_staleness` 只有 `chapter_summary / segment_summary / checkpoint` 三类（V143），`recompute.rs` 全文不出现 outline。Sherpa 的「识别变化、追踪下游影响、仅重规划受影响的部分」，StoryMoss 的「部分」还不包含计划本身。
3. **「40 项检查清单 + 80–90% 人类审阅者匹配」——清单 StoryMoss 已有约 40 项（附录 B 盘点），但从未测量过判官与作者的一致率**：editor 8 维 + prose_lint 7 项 + human_voice 8 规则 + anti_ai 5 维 + 连续性探针 5 项 + 门 grader 5 项，合计 38–41 项；`human_signals`（作者修改率）已存在于 `agency/graders.rs:180` 并在 AgencyEval 页面展示（`pages/AgencyEval.tsx:246-251`），但没有任何指标回答「编辑判的问题，作者后来改了吗」。Sherpa 用一个数字（80–90%）证明其判官可用；StoryMoss 有全部原材料，缺这个数字。

**三条补充判断**：

4. **反馈回路存在但没有回到决策**：Tab 接受/Esc 放弃/手改 diff 已进 `FeedbackRecorder` → `preference_pairs.jsonl` → `PreferenceMiner`（阈值 ≥0.5，取 3 条，`commands/intent.rs:60-140`）、风格学习（120s 防抖，≤8 条活跃偏好，`style_learning.rs:37-42`）、Agency 观察学习（+0.05/-0.1、跨书晋升 0.8/2 本，`agency/learning.rs:624-625`）。但每拍的手法池仍按**已写篇幅**轮换（`human_voice.rs:667-670`），不按作者偏好加权——学的存起来了，用的还是固定节奏。Sherpa 用留存数据训练模型；StoryMoss 的正确对位是**把作者裁决变成每拍决策的权重**，数据量（N=1）恰好够用本地统计。
5. **「季→弧→序列→剧集→场景」的中层是空位，且项目里已经挖好了坑**：StoryMoss 的规划链是 三幕书纲（`story_outlines`）→ 逐章章纲（2-4 节点）→ 节拍卡；章与书之间没有「卷/弧」的正向计划层，段摘要（每 10 章）是**回顾**不是**计划**。而 `story_contracts` 合同树里 `VOLUME` 类型已定义、读路径已实现（`story_system/contract_service.rs:101`、`domain/contracts.rs:18`、`db/models.rs:1615`），**全代码库没有任何写入方**——一个预留的空位。
6. **定位不同，不该追的最后别追**：Sherpa 是纵向整合的 IP 工厂（创作 + 分发 + 变现闭环，创作者在机器内部）；StoryMoss 是作者主权的单人工作室操作系统（本地、自带模型、101 个提示词资产可覆盖、每条判定必须引原文）。Sherpa 的护城河是数据与分发，StoryMoss 的护城河是主权与可审计性——**不要试图在数据维度与平台竞争，要在平台做不到的维度把差异做实**（第 6 节）。

| 优先级 | 借鉴项 | 一句理由 |
|---|---|---|
| **P0-1** | 检索接线：把「按需取精确上下文」接进续写路径 | Sherpa 叙事里唯一 StoryMoss「写了但没装」的模块 |
| **P0-2** | 纲层失效与局部重规划 | 「下游影响」已算到场景级，只差把章纲纳入失效物 |

## 一、Sherpa 是什么：先剥掉营销外壳

### 1.1 七步流程的机制拆解

原文的七步：① 1-2 句概念 → Sherpa 像资深编辑审视（张力/赌注/心理）→ ② 世界观/基调/人物心理 → ③ 子情节规划（故事弧→剧集→场景）→ ④ 逐场景生成（可随时引导/重写/覆盖）→ ⑤ 编辑审查（节奏/参与度下降/散文/连贯性，锁定前压力测试）→ ⑥ 一键生产（选声音→音频剧集→发布）→ ⑦ 全球规模与变现（分成 + 自动本地化）。

剥掉产品话术，这七步是四类机制：

| Sherpa 步骤 | 机制对象 | StoryMoss 对位 | 判定 |
|---|---|---|---|
| ① 概念审视 | 概念级诊断 | PROBLEM logline（`resources/prompts/agency/agency_problem_logline.md`，调用 `coordinator.rs:1873-1908`） | 有生成、无诊断三问（P2-9） |
| ② 世界与人物 | 资产构造 | 创世 Phase A/B：概念包 + 深度资产（world / 三幕 outline / foreshadowing / 角色卡含 emotional_core/trigger/wound/need，`coordinator.rs:1912-2041`） | ✅ 对等，人物心理维度更结构化 |
| ③ 子情节规划 | 层级计划 | 三幕书纲 + 逐章章纲（2-4 节点）+ 节拍卡；**无卷/弧层** | 缺中层（P1-3） |
| ④ 逐场景生成 + 人工引导 | 生成 + 人机接口 | `run_continue` + 任意指令 + Tab/Esc 幽灵 + auto_revise | ✅ 对等，接口粒度更细 |
| ⑤ 编辑审查 | 质量闭环 | 门三 grader + editor 8 维 + prose_lint/human_voice + 质量债 | ✅ 对等偏强（evidence 必引原文），缺一致率测量（P1-4） |
| ⑥ 一键生产（音频/发布） | 交付 | 导出 6 格式（md/pdf/epub/html/txt/json，`commands/export.rs:13-123`）；无音频、无发布 | 定位差异（P2-8 条件项） |
| ⑦ 全球规模与变现 | 分发经济 | 无（仅 zh-CN；订阅形态在 `src-server/`） | 平台侧能力，不追 |

### 1.2 三大技术飞跃 → 三个工程对象

**飞跃 1：叙事世界模型（状态跟踪与检索）**。原文：「构建一个演化的语义知识图谱，跟踪人物状态、秘密和情节依赖。高速度检索按需呈现精确上下文，在数百集之间维持零连续性衰减。」
工程解构 = ①知识图谱（实体/关系/状态）②检索层（按需取精确上下文）③连续性校验。「零连续性衰减」是营销修辞——检索系统做不到字面零衰减，可核验的版本是「被跟踪的事实不出现未受控的漂移」。StoryMoss 的 ①②③ 分别是：KG（7 类实体/29 类关系）+ 知识边界/物品账本/生死状态；`QueryPipeline` + LanceDB 混合检索（**未接线**）；探针（知识边界泄密/归属矛盾/死人复活/场外开场）。

**飞跃 2：层级故事规划器**。原文：「季→弧→序列→剧集→场景；渐进式规划和动态重规划，而非提前生成一切。随着故事演化，识别变化、追踪下游影响、仅重规划受影响的部分。」
工程解构 = ①多层计划结构 ②渐进式生成（用到哪计划到哪）③局部重规划（变更传播 + 影响裁剪）。StoryMoss 的 ②做到了（章纲在第一次续写该章时才生成，`coordinator.rs:4542`；节拍卡每拍现场编译）；①缺卷/弧层；③只覆盖物料不覆盖计划。

**飞跃 3：散文引擎（基于系列留存数据训练）**。原文：「基于 Pocket 自身 10 亿+ token 的故事构建，通过学习听众互动的内容、他们放弃的位置、保持他们沉迷的内容进行训练。反馈来自专用评估器模型，40 项检查清单，与人类审阅者基准测试匹配率 80–90%。」
工程解构 = ①私域创作语料 ②**行为数据奖励函数**（逐分钟留存）③以奖励函数训练的判官。「写作质量」在这里被定义成「留存预测」——这是一个**目标函数选择**，不是纯技术选择（第 6.1 节展开）。StoryMoss 用「公开共识 + 确定性规则」替代私域数据：`human_voice` 只收跨语言/跨模型世代方向一致的形态，方向矛盾项一律不入规则（v0.65.0）。两者不是同一件事，也不该是。

### 1.3 商业飞轮：对 StoryMoss 的不可复制性

原文飞轮：「更多节目 → 更多数据 → Sherpa 更好 → 更多创作者成功 → 更多创作者 → 更多节目」。这个飞轮的燃料是**平台侧行为数据**和**分发收益**，两者的前提都是「创作者在平台内部创作、作品在平台内部消费」。StoryMoss 是桌面工具：没有听众行为、没有分发渠道，这个飞轮从第一环就不成立。

但飞轮有一个**可以本地化的版本**：单个作者自己的语料飞轮。StoryMoss 已有底座——拆书（`book_deconstruction`，产物入「参考素材库」`reference_books`）、风格 DNA/仿写、Agency 观察学习跨书晋升（≥2 本书且置信度 ≥0.8 晋升为全局技能，`agency/learning.rs:622-745`）、规划模板库（`planner/template_learning.rs`）。它比平台飞轮慢（N=1），但冷启动为零、无隐私问题、反馈即时。缺的一环同样是**可测量**：晋升的资产是否让后续写作更好，目前没有指标（回到 P1-4/P1-5 的一致率与裁决率测量）。

## 三、逐项深对比

### 3.1 叙事世界模型：强在状态，弱在检索

Sherpa 的「跟踪 + 检索」是一对。「跟踪」StoryMoss 的深度已经超出大多数同类工具——知识边界分三栏（客观事实/读者认知/揭示状态）、物品归属是账本而不是快照（`item_holdings` 带 status 与取得章）、生死状态单调持久化且否定句豁免（「未气绝/假死」不算死）、时间旅行查询按章回放。**这些都是确定性、可审计的**，而 Sherpa 的 KG 只能从平台行为反推。这一半不需要借鉴。

「检索」是另一半，也是差距。具体三层：

1. **QueryPipeline 写好了没接**：四阶段（CJK bigram token 搜索 → 语义向量 → 融合 → 图谱扩展 → token 预算 → 引用编号组装，`memory/query.rs:108-453`）与 Sherpa 描述的「高速度检索按需呈现精确上下文」同构，模块头却挂着 `#![allow(dead_code)]`。项目的内部审计自己也标注过「零调用方」（`docs/AUDIT_后台资产与智能创作流程.md:99`）。
2. **生成时的上下文靠「窗口 + 硬上限」而非「按需」**：续写资产总预算 6000 字符（`continue_assets.rs:16`），前文双窗 600+1800，KG 相关设定 top-5、描述截 80 字（`memory/facade.rs:20-26`），参考场景退化为关键词重叠 top 3 且代码注释明确「同步上下文无法调 LanceDB 异步搜索」（`write_time_bundle.rs:213-226/536-540`）。这套窗口对 10 章内的连续性够用（有段摘要与检查点兜底），但「第 3 章交出去的玉佩」这类**远距离精确细节**只能靠 KG 实体或探针偶然兜住——而不是**被检索出来**。
3. **混合检索其实已经建好了**：LanceDB `hybrid_search` 的 RRF 融合（K=60，`lancedb_store.rs:390-446`）与章摘要投影入库（`projection_writers.rs:682-706`）都在，embedding 默认是本机 384 维哈希（`embeddings/embedding.rs:198-254`，有远程 provider 可换）。也就是说：**检索能力是现成的，缺的只是「在续写前用它、按结果给预算」这一步**。

对 StoryMoss 的含义：Sherpa 的「搜索基金」是向量基础设施 + 精选注入；StoryMoss 的缺口不在基建，在**接线**。这是 P0-1。

### 3.2 层级规划器：缺一层 + 缺纲层重规划

把两边的计划结构摆平看：

| 层级 | Sherpa（宣称） | StoryMoss 现状 |
|---|---|---|
| 全书 | 季 | 三幕 + 转折点（`story_outlines`，创世 Phase B 产出 `three_act_structure`） |
| 中观 | **弧 / 序列** | **空**（VOLUME 合同类型已定义、读路径已实现、无写入方） |
| 单元 | 剧集 | 章（`scenes.sequence_number`）+ 逐章章纲（2-4 节点） |
| 场景 | 场景 | 拍（节拍卡每拍现场编译） |
| 回顾物 | — | 章摘要 / 段摘要（每 10 章）/ 全书纲要 / 检查点 |

两个观察：

- **渐进式规划是平手**。StoryMoss 不在创世时把 500 章全部生成，而是「第一次续写该章时生成章纲」（`generate_chapter_outline`），节拍卡更是每拍现场编译。这一条 Sherpa 讲的内容 StoryMoss 已经在做。
- **动态重规划是单侧覆盖**。StoryMoss 的失效重算是**物料感知**的：正文指纹变了才重算摘要、段摘要、快照、关系审计（`recompute.rs:278-290`），单轮 12 章上限。这套机制的质量在同类产品里罕见（外部对比报告里 ainovel 的 `/sync` 是最近的近似物）。但 `story_material_staleness` 的三种 kind 里没有 `chapter_outline`——**改了第 3 章，第 4 章以后的章纲不受任何影响**。这不只是一个字段缺失：章纲是「计划」，而所有既有机制（级联影响报告、关系审计、摘要失效）处理的是「记录」。改稿后的计划漂移，是当前长篇工作流里真实存在的静默缺口。

对 StoryMoss 的含义：P0-2（纲层失效，复用 `cascade_impacts` 的受影响场景集合，不另起影响分析）+ P1-3（卷/弧层，用 VOLUME 合同空位）。

### 3.3 散文引擎：数据护城河 vs 主权护城河

这是两者差异最深、也最容易被误读的一条。

Sherpa 的做法：**用听众行为定义「好看」**。1B+ token 的自家故事语料 + 逐分钟留存曲线训练出「散文引擎」，再用 40 项清单的评估器模型（与人类审阅者 80–90% 匹配）做生成时反馈。它的对象是**留存率**：听众在哪一分钟弃剧，模型就往「不弃剧」的方向调。

StoryMoss 的做法：**用公开共识定义「不像机器」**。`human_voice` 只收跨语言、跨模型世代方向一致的形态（句长离散度、语气词缺失、情绪具身化独大、连词堆叠、双音节填充、花式对话标签、抽象包装、段落过匀），方向矛盾项（标点密度、平均句长、词汇多样性）一律不入规则——目的恰是避免「把 AI 特征反向拉满造出新的机器感」（sepia 分布偏移论点）。写作端 7 条准则 + 8 手法池按篇幅轮换；审查端 editor 配白名单与「不得据此判 blocking」纪律。

两者不是同一件事：

| 维度 | Sherpa | StoryMoss |
|---|---|---|
| 语料 | 10 亿+ token 私域创作 + 行为数据 | 无（提示词 + 确定性规则 + 作者自己的手改） |
| 奖励信号 | 听众留存（平台收益代理） | 作者意图（Accept/Reject/手改 diff） |
| 目标 | 让人停不下来 | 让文本像人写的、且是**这个作者**写的 |
| 判官 | 专用评估器模型（训练产物） | LLM editor + 确定性规则（evidence 必引原文） |
| 可审计 | 概率输出 | 规则命中可引用、可复现 |

**结论：StoryMoss 无法复制也无法公平比较前两列，但也不需要。**平台的目标函数是留存，工具的目标函数是作者意图。用「读者停不下来」去优化一本作者想写成的书，是一次静默的目标函数替换（Goodhart 风险：留存优化会系统性地选择「预支答案/预告腔/每千字一个钩子」，这正是 v0.65.1 叙事架构层明令禁止的形态）。这一点在文档里要写死：**当未来引入任何行为数据（哪怕只有本机阅读时长）时，只能作为 advisory 指标，不得成为写作目标。**

而 StoryMoss 真正能从 Sherpa 借鉴的是最后两列的反向工程：**判官必须被测量**（80–90% 是 Sherpa 公开承诺的判官质量；StoryMoss 的判官从未与它的「人类审阅者」——作者——对齐过）。这是 P1-4。

### 3.4 评估器：清单数量已对等，差的是一致率

把 StoryMoss 散落的检查项按层盘点（详见附录 B），合计 38 项（追读力三要素展开则 41 项），与 Sherpa 宣称的 40 项同量级。形态对比：

| | Sherpa 40 项清单 | StoryMoss ≈40 项 |
|---|---|---|
| 载体 | 评估器模型（训练产物） | 8 维 LLM editor + 20 项确定性规则（prose_lint/human_voice/anti_ai）+ 5 项连续性探针 + 5 项门 grader（合计 38） |
| 是否可引用 | 未知（模型输出） | 确定性项必须引原文；editor blocking 必须带 `evidence` |
| 是否逐项记分 | 未知 | editor 有 `dimension_scores` 8 维；确定性项有 findings 明细 |
| 逐项回归探针 | 未知 | **部分**（human_voice 探针、三把尺子契约、冲突复述契约；未做到逐项矩阵） |
| 判官一致率 | **80–90%（公开数字）** | **未测量** |
| 判官档位 | 专用评估器模型 | editor 默认落 Background 档（`llm/service.rs:267-280` 显式映射） |

两个直接可移植的启发：

1. **一致率测量是本地可做的**，而且不需要新数据源：editor 的 blocking_issues 必带原文引用（`agency_editor_auditor_system.md:31-41`），作者改完之后，**引用是否在成稿里幸存**就是天然的判定：引用原样保留 = 作者不同意/忽略；引用被改写或删除 = 作者采纳。配合已有的 `modification_ratio`（`graders.rs:180-241`）与 `auto_revise(editor_qc)` 历史（`agents/commands.rs:327-608`），可以算出「编辑命中率 / 采纳率 / 误报率」三个指标，展示在 AgencyEval（该页已有 human-signals 卡片，`AgencyEval.tsx:246-251`）。
2. **判官档位应当是显式策略**。Sherpa 用专门训练的评估器（贵重资产）做判官；StoryMoss 的映射把 editor 默认放 Background（成本导向）。合理的中间态：把「评审模型档位」做成可见设置 + 由第 1 条的一致率数据反过来指导它该不该升档——即**用测量结果配置判官，而不是拍脑袋**。

### 3.5 分发与变现：平台 vs 工具

Sherpa 的⑥⑦两步（音频生产、全球分发、分成变现）不是技术模块，是**渠道所有权**。StoryMoss 没有任何分发渠道，追这两步等于在别人的战场打仗。但要做两件事：

- **在定位上明确说清**：StoryMoss 的交付终点是「作品离开工具时是就绪的」（EPUB/PDF 已有，`commands/export.rs:13-123`），不是「作品上线了」。这条差异是价值观，不是功能缺失。
- **给最后一公里留一个条件项**（P2-8）：投稿包（正文 + 简介 + 章节钩子清单 + 标签语料）与有声化导出（TTS 分章 + 角色声线分配）。触发条件写死：**作者自己有分发渠道或明确要求时才做**——没有渠道时，音频是成本而不是价值。

### P0-1 检索接线：让「按需取精确上下文」进入续写路径

- **设计要点**：

  3. 注入位置进 prompt 顺序契约（现为 卡全文→人物锁→状态网→Bundle→指令→卡摘要→状态摘要→文笔基线→末句锚点，`beat_card.rs:876-923`）——更新 `render_writer_user_prompt` 的顺序契约测试（`beat_card.rs:1099/1141`），这是有意的契约变更。
  4. 无命中时整块不出（不产生空块噪音）；embedding 用当前激活 provider，未配置时哈希兜底（会损失语义召回，但这属于 P2-7 同类问题，不阻塞接线）。
- **验收**：
  - 单测：fixture 故事在第 3 章埋「玉佩交给苏会山」，写第 40 章（节拍卡含「玉佩」）→ 断言检索块召回到第 3 章；无关节拍卡 → 断言无块。

### P0-2 纲层失效与局部重规划

- **借鉴源**：Sherpa「识别变化、追踪下游影响、仅重规划受影响的部分」。
- **现状锚点**：`story_material_staleness` 三类 kind 无 `chapter_outline`（V143；`recompute.rs` 全文无 outline）；编辑旧章的触发点已存在（`scene_commands.rs:346-357`）；受影响场景集合已由级联影响报告自动产出（`impact_report.rs`、`scene_service.rs:263`）。
- **设计要点**：
  1. 新增失效 kind `chapter_outline`：编辑第 N 章时，对「编号 > N 且已有章纲」的章记失效，`from_chapter` 取最早者；受影响范围**优先复用 `cascade_impacts`**（有影响分的场景），无影响数据时退化为「该章之后所有已有章纲的章」。
  2. 运行维护页（`pages/Maintenance.tsx`）展示「受影响章纲 N 条」+ 逐条/批量「按正文重规划」，调用既有 `generate_chapter_outline`（`coordinator.rs:4214-4419`）并复用 12 章/轮上限模式（`AUTO_RECOMPUTE_MAX_CHAPTERS`）。
  3. 重规划结果**必须经作者确认**再落库（与「报告不自动改写」的既有哲学一致，V134 `user_created` 保护同精神）。
- **验收**：探针——编辑第 3 章后断言第 4 章起章纲标记失效；重规划后标记清除且新章纲引用了重算后的摘要；不改正文时无标记。

### P1-3 卷/弧中层计划（VOLUME 合同空位）

- **借鉴源**：Sherpa「季→弧→序列→剧集→场景」。
- **现状锚点**：`VOLUME` 合同类型已定义、读路径已实现、**无写入方**（`contract_service.rs:101`、`domain/contracts.rs:18`、`db/models.rs:1615`）；三幕书纲（创世 Phase B）+ 逐章章纲之间无正向计划；段摘要（每 10 章）是回顾物。
- **设计要点**：
  1. 卷纲资产（VOLUME 合同 JSON）：卷号/章节范围/卷目标/卷末高潮/须兑现伏笔/新开线索预算/规模估计。
  2. 生成时机：创世时若规模估计超阈值（如 >60 章）生成第一卷；**每卷边界渐进生成下一卷**（与逐章生成章纲的渐进哲学一致）；卷末自动提示 + 作者确认。
  3. 注入：章纲生成（`generate_chapter_outline`）时带「当前卷目标 + 卷内进度」；compass（`story_system/compass.rs`）的规模估计接卷纲。
  4. 与 P0-2 联动：卷纲也在失效物范围内（kind 增 `volume_outline`），但重规划粒度是「影响该卷目标的事实」而非逐章。
- **验收**：合同读写契约测试（写入 VOLUME → `get_contract_tree` 可见）；探针——章纲 prompt 含卷目标；幕前/幕后可查看卷纲；短篇（不触发卷纲）行为不变。

### P1-4 判官一致率（editor agreement）

- **借鉴源**：Sherpa「评估器与人类审阅者基准测试，匹配率 80–90%」。
- **现状锚点**：editor blocking 必带 `evidence` 原文（`agency_editor_auditor_system.md:31-41`）；`modification_ratio` 已存在（`graders.rs:180-241`）；AgencyEval 已有 human-signals 卡片（`AgencyEval.tsx:246-251`）；`auto_revise(editor_qc)` 修订历史可查（`agents/commands.rs:327-608`）。
- **设计要点**：
  1. **引用幸存判定**（确定性）：对每章 editor blocking 的 `evidence` 引用，取成稿文本，计算引用是否存活（近逐字匹配，容错阈值可调）。删除/改写 = 采纳；原样保留 = 未采纳。
  2. 三个指标：命中率（blocking 数/千字）、采纳率（被改动的引用占比）、误报率（作者在随后 N 章回退/撤销的比例，用现有 feedback 事件）。
  3. 落点：`agency_eval_overview` 聚合（`agency/commands.rs:356-453`）+ AgencyEval 新卡片；**只报不改**（不做自动降权，先积累数据）。
  4. 配套：评审模型档位在设置页显式化（当前 editor→Background 是硬映射，`llm/service.rs:267-280`），一致率数据出来后可作为升档依据。
- **验收**：单测（构造「引用删除/保留」两种成稿断言判定）；AgencyEval 渲染测试；真机跑 3 章报告三个数字（人工核对 1 样本）。

### P1-5 作者裁决回灌每拍决策（手法池按偏好加权）

- **借鉴源**：Sherpa「学习听众互动的内容……进行训练」——本地化为「学习作者的裁决……影响下一拍」。
- **现状锚点**：Tab/Esc/modify 已入 FeedbackRecorder + PreferenceMiner（`commands/intent.rs:60-140`）；手法池按已写篇幅轮换（`human_voice.rs:667-670`），与偏好无关；每拍实际使用的手法在节拍卡编译时可知（`beat_card.rs:910`）但**没有落库与反馈关联**。
- **设计要点**：
  1. 落库每拍的手法 id：在 beat 落库时写 `(story, chapter, beat_index, technique_id, guidance_version)`（新列或小表）。
  2. 反馈关联：accept/reject/modify 事件按场景+章号 join 到最近一拍的手法 id。
  3. 加权轮换：每手法统计「接受率 / 平均修改率」，样本 ≥5 后进入加权（在确定性轮换的候选里按权重排序，仍保持给定统计下确定性可测）；样本不足时退回现行轮换。
  4. 不做黑箱：权重与统计在「学习中心」（`pages/AgencyLearning.tsx`）可见可重置。
- **验收**：纯函数加权单测（含确定性）；探针——连续 10 拍记录后统计累计；「重置统计」后回到基线轮换。

### P2-6 长篇稳定性回归门

- **借鉴源**：「零连续性衰减」的可核验形态。
- **现状锚点**：golden harness 已有单次续写指标（output_chars / self_repetition_ratio / prior_overlap / advanced / probe_gaps / change_delta_honored，`agency/golden_harness.rs:1-61`，`#[ignore]` 门控）；探针都已存在（泄密/归属/死者/冲突复述）。

## 六、定位启示

### 6.1 两个目标函数，不要混

Sherpa 的一切设计服务于**听众留存**（平台收益代理）：评估器以留存数据训练、散文引擎以留存数据调优、情节规划偏向「不弃剧」。StoryMoss 的一切设计应服务于**作者意图**：文笔基线以「像人写的」为方向、叙事架构层明确拒绝套路化收束（v0.65.1：不做「理解+接受+成长」三脚架、不预支答案）、质检以可引用证据说话。

这两套目标函数在多数时候同向（都反对机器腔、都要求情节推进），但在关键处**必然分叉**：留存喜欢「预支答案、章章钩子、每千字一个爽点」，文学性喜欢「迟一拍揭示、无用细节、不体面的举动」。因此：

- StoryMoss 的任何新评估信号（包括 P1-4 的采纳率、P1-5 的偏好权重）都只回答「作者是否满意」，**不回答「读者是否会留下」**。
- 未来若引入哪怕本机的阅读行为数据，只能作 advisory 展示，不得进入写作目标。

### 6.2 数据护城河 vs 主权护城河

不要把 StoryMoss 摆进「谁的数据多」的赛道。Sherpa 的对比叙述应该是：

> 平台把创作变成数据管道：你的稿子训练它的模型，你的读者是它的留存曲线，你的收益是它的分成比例。
> StoryMoss 把管道交回作者：101 个提示词资产可覆盖（`prompts/registry.rs`、`PromptsPanel`；热路径 5 条 system 常量刻意不可覆盖，作为文笔准则送达的最后保证）、文风偏好是你自己的手改提炼的（`style_preferences`）、每条 AI 判定必须引你的原文（editor evidence 契约）、成本每 run 有熔断（30 万 token）与哨兵（50 万提示）、离线可用（本地哈希 embedding 兜底）。

主权护城河的四个现存支点（都已在代码里）：**可覆盖的提示词资产**（101 个 + 覆盖落库）、**可审计的判定**（evidence 必引原文 + 白名单纪律）、**可控制的成本**（run 预算 + 哨兵 + 角色档位）、**可离线的运行**（本地 provider 兜底）。这四条是平台模式结构性给不出的——而它们现在**没有被任何文档系统性地讲成卖点**，值得进 README/USER_GUIDE 的定位段落。

### 6.3 「单人工作室」叙事可直接借用

Pocket FM 用「一人工作室资源池」「单人工作室创作价值数百万的节目」讲创作者经济学——这套叙事本质上描述的就是 StoryMoss 的产品形态：幕前（沉浸写作）+ 幕后（资产管理/质检/成本/学习）**就是单人工作室的操作系统**。差别只在 Sherpa 是平台内置的生产线，StoryMoss 是作者自有的工作室。文案层可直接采用「单人工作室」框架，并把三个页面（运行维护/级联中心/学习中心）讲成「工作室的质检部、编辑部、复盘部」。

### 6.4 N=1 的作者就是正确的地面真值

Sherpa 需要百万听众的留存曲线才能定义质量；StoryMoss 只需要一个人的裁决。这不是劣势——**作者是唯一有资格定义「这本书该是什么样」的人**。缺的是把裁决变成可测量的信号并回灌决策（P1-4/P1-5）。当这两个回路接通后，StoryMoss 会拥有一个 Sherpa 结构上得不到的东西：**一个只属于这个作者的、可解释的、本地闭环的质量模型**。
